# MallMind AI — Model Service (Phase 5: Data Science)

Python service holding the two Data Science models required by the spec
(Part 4, Module 4): a content-based **product recommendation engine** and a
**product/category demand prediction** model. Exposed to the Java backend
over REST via FastAPI (Part 3.3 / Part 10).

## Setup (Windows, PowerShell)

```powershell
cd model-service
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

| File | Source | Notes |
|---|---|---|

## Model 1: Content-based recommendation engine

- **Code:** `app/recommendation.py` (`ProductRecommender`)
- **Method:** category/brand/color one-hot + min-max-scaled price → cosine
  similarity. Hard filters (availability, budget) applied before ranking.
- **Baseline:** plain category+budget filter, catalogue-id order, no ranking.
- **Evaluate (trains + evaluates + writes results):**
  ```powershell
  .venv\Scripts\python.exe app\evaluate_recommendation.py
  ```
- **Real results from this run** (`models/recommendation_eval_summary.json`,
  k=5, 32 test queries — one per category + a brand-aware variant per category):

  | Metric | Content-based model | Category-filter baseline |
  |---|---|---|
  | Precision@5 | 0.725 | 0.763 |
  | Recall@5 | 0.767 | 0.749 |
  | NDCG@5 | **0.885** | 0.826 |

  The model ranks relevant items higher (NDCG) and recalls slightly more;
  the baseline's hard category pre-filter gives it a small structural edge
  on raw precision. See the notebook for the full interpretation and a
  documented limitation (colour is a soft signal, not a hard filter — if a
  category has zero items of the requested colour, the model still returns
  its closest category+price match rather than an empty list).

## Model 2: Demand prediction

- **Code:** `app/demand_prediction.py`
- **Method:** RandomForestRegressor on lag_1/lag_7/rolling_mean_7/
  day_of_week/is_weekend/day_index/category, trained on a **per-category,
  chronological** 80/20 split (never shuffled — no leakage).
- **Baseline:** 7-day trailing moving average.
- **Evaluate (trains + evaluates + writes results + saves the model):**
  ```powershell
  .venv\Scripts\python.exe app\evaluate_demand.py
  ```
- **Real results from this run** (`models/demand_eval_summary.json`, 752 test rows):

  | Metric | Random Forest | Moving-average baseline |
  |---|---|---|
  | MAE | **2.91** | 3.52 |
  | RMSE | **3.94** | 4.92 |

  ⚠️ Both numbers describe a **simulated** series's predictability, not
  real consumer demand — see the data label in `notebooks/02_demand_prediction.ipynb`.

## Running the FastAPI service

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8001
```

Endpoints (all verified live):
- `GET /health`
- `POST /recommendations` — body: `{"category","brand","color","max_budget","max_results"}`
- `GET /demand/{category}/predict`

The service loads `data/catalog.csv` and `models/demand_model.joblib` at
startup. If either is missing, the corresponding endpoint returns `503`
rather than crashing the whole service (Part 10: graceful degradation —
the Java backend must keep working on plain search/navigation even if
this service, or one model within it, is unavailable).

## Model 3: Text intent classification (Deep Learning Model 1)

- **Code:** `app/intent_classifier.py` (TextCNN), `app/entity_extraction.py` (separate, rule-based)
- **Dataset:** `data/generate_intent_dataset.py` — template-generated, ~1,800 labeled
  queries across 6 intents (`SHOP_SEARCH`, `PRODUCT_SEARCH`, `NAVIGATION`,
  `FACILITY_SEARCH`, `PRODUCT_COMPARE`, `REFINE_SEARCH`), filled with real catalogue
  entity values. **Disclosed as synthetic**, not real visitor queries.
- **Train + evaluate:**
  ```powershell
  .venv\Scripts\python.exe app\evaluate_intent.py
  ```
- **⚠️ Two numbers are reported, on purpose** — see `app/evaluate_intent.py`'s
  docstring and `notebooks/03_intent_classification.ipynb` §6 for the full
  methodological reasoning:

  | Split | Test accuracy | Macro F1 | What it actually measures |
  |---|---|---|---|
  | Example-level (random split) | ~1.00 | ~1.00 | Memorization of the fixed templates — misleadingly optimistic |
  | **Template-level (held-out phrasings)** | **~0.64** | **~0.59** | **Genuine generalization to unseen phrasing structures — the honest number** |

  The large gap is itself the finding: a small template-generated dataset lets a
  model memorize surface patterns almost perfectly while still being a mediocre
  real-world intent classifier. Reporting only the first number would be
  dishonest (Part 17 rule #8). The service loads the **template-level** model.
- **Served via:** `POST /nlu/intent` — returns intent + confidence + a
  `low_confidence` flag + extracted entities in one call.

## Model 4: Product image classification (Deep Learning Model 2)

- **Code:** `app/image_classifier.py` (ResNet18 transfer learning), Grad-CAM in `app/evaluate_image.py`
- **Dataset:** `data/prepare_image_dataset.py` — **Fashion-MNIST** (Zalando Research,
  **MIT License**), 10 classes grouped into 3 real platform categories (Apparel,
  Bags & Accessories, Footwear). MallMind's other 13 categories have no licensed
  image dataset available and are **out of scope** for this model — stated
  honestly, not glossed over.
- **Train + evaluate (downloads Fashion-MNIST once, ~30MB):**
  ```powershell
  .venv\Scripts\python.exe data\prepare_image_dataset.py   # one-time dataset prep
  .venv\Scripts\python.exe app\evaluate_image.py
  ```
- **Real result:** 99.2% test accuracy, macro F1 0.992 (720 held-out test images,
  240/class — see `models/image_eval_summary.json` for the full per-class
  precision/recall/F1 and confusion matrix). Genuinely high and not a leakage
  artifact — these 3 categories are visually very distinct even at low resolution.
- **Served via:** `POST /vision/classify` (multipart file upload) — returns
  category + confidence + a `low_confidence` fallback flag; always states that
  only 3 categories are recognized.

## Voice assistant speech I/O (Phase 7, Part 15)

This service only converts audio↔text -- it holds no conversational logic.
The Java backend's `VoiceAssistantService` (`backend/src/main/java/com/
mallmind/backend/service/voice/`) calls this service's `/voice/transcribe`
and `/nlu/intent`, then answers using its own real product/shop/navigation
data, then calls `/voice/speak` for the spoken reply. See root
`PROGRESS.md`'s Phase 7 section for why that split exists and for a real,
verified multi-turn conversation example.

- **Code:** `app/speech.py`
- **STT:** `faster-whisper` (`base.en`, CPU, int8). Uploaded audio is
  decoded and resampled to 16kHz mono **entirely in memory** -- never
  written to disk (Part 17: don't retain voice recordings).
- **TTS:** Windows SAPI5 via `pyttsx3`. Its only API writes to a file, so a
  temp WAV is unavoidable -- it's deleted immediately after being read back
  into memory.
- **Endpoints:** `POST /voice/transcribe` (multipart audio file ->
  `{"transcript": str}`), `POST /voice/speak` (`{"text": str}` -> WAV bytes).
  Both return 503 if their underlying model/engine failed to load, matching
  every other endpoint in this service (Part 10: degrade gracefully).
- **Verified live, real round trip:** this service's own `/voice/speak`
  synthesized "Where is the nearest washroom?", that WAV was POSTed to the
  Java backend's `/api/voice/query`, which called back into this service's
  `/voice/transcribe` and got the identical sentence back, then correctly
  classified `FACILITY_SEARCH`, resolved a real route, and returned a
  spoken reply synthesized by this same service's `/voice/speak`.
- Known limitation: `base.en` is English-only and the smallest model that
  gave reliable transcription of catalogue brand/product words in testing --
  a noisier real microphone input would transcribe less reliably than the
  clean synthesized test audio used here.

## Known limitations

- The recommendation engine has never seen real visitor feedback; its
  relevance labels are a documented rule-based proxy, not real click/
  purchase data (see the notebook for the exact rule).
- The demand model trains on simulated data; swapping in a real
  `search_events` aggregation is a one-line change to `evaluate_demand.py`
  once enough history exists in production.
- The intent classifier's honest (template-level) accuracy is ~64%, not the ~100%
  a naive random split would suggest — real deployment would need a much larger,
  genuinely human-authored and consented query dataset to improve this.
- The image classifier recognizes only 3 of 16 platform categories (licensing).
- The recommendation, demand-prediction and image-classification endpoints
  are still only tested standalone, not called from the Java backend yet
  (the rest of Phase 9) — the intent/entity and speech endpoints *are*
  now called from Java, as of Phase 7's voice assistant.
- The voice assistant's `REFINE_SEARCH` vs. fresh-search distinction
  inherits the intent classifier's ~64% honest accuracy: an utterance that
  should refine an existing search is sometimes misclassified as a new
  search, which clears the remembered filters instead of merging into
  them. This is the Phase 6 model's documented limitation surfacing in a
  new place, not a bug in the Java-side conversation manager.
